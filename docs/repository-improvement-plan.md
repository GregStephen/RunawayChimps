## September 12 spawn-hand initialization follow-up

**Confirmed failing runtime feedback:** Greg reports that players' hands can become stuck in the floor when they spawn unless the physical hands/controllers are already held up. This is a failed XR spawn/locomotion case, not a player instruction; players must not need a special pose to enter the game.

**Source finding:** `RigSpawnSnapper` freezes the complete rig collider hierarchy during startup placement, but `GorillaLocomotion.Player.ResetAfterTeleport()` previously seeded `leftHandFollower` / `rightHandFollower` and their cached last positions directly from `CurrentLeftHandPosition()` / `CurrentRightHandPosition()`. Gorilla locomotion's first update could therefore begin from a controller-derived hand position already beyond walkable geometry. Because hand contact drives body displacement and sticky contact state, simply snapping a buried hand upward after locomotion resumes can itself create a first-frame push or launch.

**Implemented on `fix/spawn-hand-floor-stick`:** `Player.ResetAfterTeleport()` now sweeps from the arm root toward each tracked desired hand using the existing locomotion collision path. A meaningfully displaced hand is initialized at the first safe contact and temporarily suppressed as a push/contact source until the tracked pose becomes reachable; a 0.015 m prototype tolerance prevents ordinary low or surface-touching hand poses from being treated as invalid. This shared reset path covers Hub startup, sector travel, capture respawn and `RigFloorPenetrationGuard` recovery. `Tools/validate_level1_contracts.py` now protects the spawn-safe hand source contract. PR #14's Source validation workflow passes for the implementation commit; that is source evidence only, not XR runtime proof.

**Pending validation:** Unity 2022.3.55f1 compile/import first. Headset-test cold Hub startup with hands down at the sides, controllers near the floor/on the lap, one hand low and both hands low. Required result: no hand is seeded below the floor, no player launch/jitter/pin occurs, normal low hand contact remains possible, and an initially obstructed hand re-arms cleanly when lifted. Repeat Hub → Level 1, Level 1 → Hub, Level 1 completion → Level 2, RETURN TO SECURITY, Crawler capture respawn, recentering and two-client Photon. Do not mark the defect resolved until those runtime tests pass.

## September 11 Hub and Level 1 spawn/arrival stability follow-up

**Confirmed failing runtime feedback:** Greg originally reported that the local player could occasionally begin partially inside the Hub floor and that two Hub → Level 1 transitions produced severe arrival glitching. The first follow-up added three fixed settle steps, a 0.06 m floor skin, repeated grounding and body/head clearance checks. Greg's latest runtime test confirms that this settle-only approach **still fails intermittently**: the local Gorilla can still become stuck in the floor. The earlier implementation must therefore be treated as failed validation, not as a resolved spawn/travel issue. This is a reliability defect; it does not change any intended spawn marker, arrival route or level flow.

**Updated source finding:** Bootstrap and sector travel use separate rig-placement paths, but the deeper conflict is in the persistent Bootstrap rig hierarchy. `Bootstrap.unity` configures the `XROrigin` with `GorillaPlayer` itself as the `CameraFloorOffsetObject`; that same `GorillaPlayer` object owns the Rigidbody/body capsule and parents the tracked head and both hand colliders. The previous Hub startup snap disabled locomotion and the body/head colliders but left the hand colliders live, so XR tracking-origin adjustment and compound-Rigidbody physics could still affect the same hierarchy while it was being positioned. The previous Hub grounding ray also sampled the floor under the authored spawn marker X/Z and then used that height for the actual body capsule. In room-scale/headset-offset cases the body capsule does not have to share the marker's exact X/Z footprint, so that floor sample can be valid for the marker while still being wrong for the physical capsule. `PlayerSpawner` remains responsible only for the network-avatar pose, not the local Gorilla locomotion body's floor placement.

**Strengthened implementation on `codex/fix-level1-crawler-lighting`:** `RigSpawnSnapper` now freezes `GorillaLocomotion.Player`, the Rigidbody and **every collider under the XROrigin** (including both hands) before startup placement. It waits for the XR `CameraFloorOffsetObject.localPosition` to remain stable for consecutive rendered frames, aligns camera yaw/XZ to `HubSpawn`, and grounds from a ray placed beneath the actual body-capsule center rather than beneath the marker. During fixed settling, any new XR floor-offset movement resets the stability counter. The rig then gets one final rendered XR update while still frozen, is grounded again, has clearance rechecked, and only then restores the entire collider set and dynamic physics. The existing sector-travel/capture-respawn path still performs its multi-fixed-step frozen placement and clearance checks.

**Post-release recovery implemented:** new `RigFloorPenetrationGuard` is created on the persistent Bootstrap rig at runtime. It is a last-line safety net for a late XR tracking-origin/recenter or physics adjustment after startup, sector travel or capture respawn. It does not pin the player to the ground and never pulls the player down. Once AppState is ready and travel is not busy, it compares the real body-capsule bottom with a same-scene upward-facing locomotion surface directly under the actual body footprint. Only verified shallow penetration is corrected by temporarily disabling Gorilla locomotion, making the body kinematic, lifting the XROrigin by the measured penetration plus a small recovery skin, resetting locomotion caches, and restoring physics. The persistent physics probe uses a fixed `RaycastHit` buffer with `Physics.RaycastNonAlloc`; it ignores rig-owned colliders and support surfaces above the capsule center. It logs a recovery warning for diagnostic evidence and refuses automatic correction beyond its bounded recovery depth.

**Pending validation:** Unity 2022.3.55f1 compile/import first. Then repeat cold Hub startup enough times to catch the former intermittent case, including standing, crouching, room-scale offsets and recentering. Include hands-down starts from the September 12 follow-up: both hands at the sides, one controller low, both controllers low/on the lap, then lift/re-lower each hand. Repeat Hub → Level 1, Level 1 → Hub, Level 1 completion → Level 2, RETURN TO SECURITY and Crawler capture respawns. Required result is no floor penetration, jitter/launch, stuck hands, stale velocity or delayed physics kick. Watch for `[RigFloorPenetrationGuard]` warnings: an isolated recovery proves a late XR/physics displacement occurred and was caught, while repeated recoveries are still a **failed validation** and should trigger deeper tracking-origin/rig-ownership investigation rather than being accepted as normal behavior. Two-client Photon and target Quest validation remain required; source inspection cannot establish that the intermittent issue is resolved.

## September 12 Level 1 vent headlamp and proposed equipment UX

**Confirmed design/implementation change:** Greg approved the previously proposed Level 1 vent headlamp. `VentHeadlampController` is now source-implemented on `codex/fix-level1-crawler-lighting`. It installs on the persistent local `XROrigin`, creates/reuses one `Local_Vent_Headlamp` Spot Light under the tracked XR camera, starts with the utility equipped for this prototype, and enables/fades the beam only while the local zone is `Level1_Vents`. Current tuning is approximately 46° outer cone / 30° inner cone, 8 m range, 1.8 intensity, cool-white color, 0.14 s fade, no realtime shadows and no bounce contribution. These are prototype presentation values, not final art settings.

**Local-only multiplayer rule implemented for the real beam:** the Spot Light is not represented in Photon properties and no remote avatar creates another realtime headlamp Light on this client. Each player therefore gets at most their own real gameplay beam, which prevents a ten-player vent from becoming ten dynamic spotlights and avoids another player's equipment washing out the local horror presentation. The ambient/fill baseline must remain independently navigable; the headlamp is a focus/atmosphere tool, not permission to make Level 1 globally black again.

**Cosmetic/equipment source finding:** the current Photon avatar already has cosmetic slots including `Head` and `Face`, and `PhotonVRManager` stores/synchronizes cosmetics through the `Cosmetics` property. Gameplay tools should not overload that appearance state. A top hat must remain a top hat rather than automatically gaining or being replaced by a lamp. The proposed equipment architecture therefore uses separate utility state/mounts such as `UtilityHead`, `UtilityWrist` and `Handheld`; large head cosmetics may need a forehead/temple/under-brim fallback mount. Remote players can later see a small utility housing/emissive lens without receiving a real dynamic Light by default.

**Proposed, not implemented:** a larger inventory/loadout menu in the Hub/safe rooms plus a 3–5 slot radial quick utility wheel for in-level switching. Exact Quest controller binding remains open because source inspection did not identify a Runaway-Chimps-specific face-button mapping safe to claim. Do not steal Grip/Trigger from grabbing/locomotion. The current headlamp controller already separates `toolEquipped` from zone activation and exposes `SetToolEquipped(bool)`, so future wheel code can equip/stow it without rewriting the light. Other tool ideas—UV/inspection mode, wrist scanner, throwable noise decoy, noisy pry/maintenance tool and co-op beacon—remain proposals only; avoid adding tools without a distinct gameplay decision/risk/reveal. See [Tool inventory, utility wheel, and multiplayer equipment concept](tool-inventory-and-equipment-concept.md).

**Pending validation:** Unity 2022.3.55f1 compile/import; both safe-room→vent and vent→safe-room transitions; repeated Level 1 re-entry with no duplicate light; no beam in Hub/Loading/Level 2; beam aim and material response in-headset; possible no-shadow light bleed through vent corners; two-client confirmation that each client receives only its own real illumination; and target Quest frame-time/memory impact. Remote equipment hardware, equipment Photon state, cosmetic mount overrides, wheel UI and controller bindings are not implemented and must not be mistaken for missing headlamp-light synchronization.

## September 11 Crawler visual-path and animation correction

**Confirmed failing runtime feedback:** after the earlier Level 1 follow-up, Greg reported that Zombie Crawl still showed no visible crawl animation, could appear several meters away from the invisible gameplay rig that was sliding through the vents, and could render outside the vent. Its long body also cannot negotiate a 90-degree turn convincingly if the whole imported model is rigidly rotated around one navigation-root pivot. The earlier animation-speed/restart source changes are therefore not runtime-validated and must not be described as a completed visual fix.

**Source finding:** the pre-correction `CrawlerVisualController` already placed the imported Zombie object at local position zero beneath the gameplay root, so the multi-meter visual separation is not explained by retaining its old scene-root position. The likely alignment problem is the FBX/skeleton's internal body pivot relative to its GameObject root. The Zombie uses a Generic rig and its controller contains one default `mixamo_com` state. A state can advance while the intended bones remain visually static if the standalone animation bindings do not match the imported skeleton; this must be detected directly instead of hidden behind speed tuning. Separately, no rigid long child can keep its rear body in the old corridor while its front has already entered a perpendicular corridor.

**Implemented on `codex/fix-level1-crawler-lighting` in `5f5ea84` and `97b20e6`:** `CrawlerVisualController` now creates a dedicated visual anchor and keeps navigation/capture/Photon authority on the existing gameplay root. New `CrawlerBodyPathFollower` resolves the Generic Mixamo chest/spine/hips chain by normalized bone names, aligns the visible front-body anchor to the gameplay leader rather than trusting the FBX origin, and uses render bounds for initial floor placement. It records recent root motion through the vent and makes torso bones sample progressively older positions/headings so the front can enter a turn while hips/rear remain on the prior path. The history is seeded straight behind the leader on initialization and teleport so the torso cannot collapse before real motion history exists. Animated hands use bounded non-allocating wall checks to keep an obviously penetrating hand just inside encountered vent surfaces. The crawl Animator is explicitly rebound/entered into `mixamo_com`, kept `AlwaysAnimate`, and probed for actual limb-bone motion while the root is moving. If state time advances without probe movement, the controller attempts one rebind/restart and then emits a persistent clip/skeleton binding error instead of silently sliding forever. Photon still synchronizes only the gameplay root/chase state; each client derives visual bending locally.

**Implementation note:** the earlier recommendation considered Unity Animation Rigging for the corner deformation. The current source implementation instead performs lightweight Generic-bone correction after Animator evaluation, avoiding a runtime RigBuilder/constraint graph for this prototype. Animation Rigging remains installed and can still replace the final hand correction with authored/two-bone IK if playtesting shows unacceptable arm stretch. This is an implementation-detail choice, not a change to the confirmed requirement that the long visible Crawler stay inside the vent path through corners.

**Pending validation:** Unity 2022.3.55f1 compile/import first. In a straight vent confirm the visible chest/body now sits on the gameplay path and its rendered floor contact is correct. Prove `mixamo.com.anim` actually deforms hands/forearms/head and that the persistent binding error does not fire. Verify the seeded body starts extended, then inspect a 90-degree corner and junction for wall escape, twisting or collapse. Inspect hand correction for unnatural stretching; if needed, preserve the same safe targets but drive them through two-bone IK. Repeat patrol/chase speeds, capture and safe-room behavior after the visual changes, then validate a two-client Photon controller handover and target Quest performance. Do not mark the crawl/corner issue resolved until those runtime checks pass.
