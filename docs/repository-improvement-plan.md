## September 13 Level 1 keycard-room environment and regeneration lore

**Confirmed design direction:** the currently sparse Level 1 keycard safe room is no longer intended to become another surveillance/monitor space or a conventional operating room. It should be authored as a **regeneration/tissue-damage testing laboratory**. The room's gameplay purpose remains unchanged: it is the safe destination reached by either vent route and contains each player's fixed personal staff-access card. Its new environmental purpose is to make that card feel discovered in a believable lab workspace and to reveal the facility's broader destructive regeneration program.

**Confirmed story boundary:** do not turn this room into a second Crawler escape origin. The existing Level 1 escape evidence remains the damaged cage plus scratches/blood leading from that cage toward the vents. The keycard room must not add a broken restraint or trail that implies the Crawler escaped from there too. Whether this exact room treated this exact Crawler, any subject number, and the exact trial/procedure history remain intentionally undefined.

**Planned environment work, not implemented:** dress the room with a restrained low-poly laboratory language that communicates regeneration testing without another monitor wall: possible testing/restraint hardware, chemical-delivery equipment, sample/cold storage, biological-waste handling, anatomy/regeneration diagrams, carts and treatment supplies. Integrate the fixed card into a believable staff-owned location such as a lab coat, clipboard, badge reel or workstation dock. Those individual prop choices are proposals until the room layout/art pass confirms them.

**Implementation/validation boundary:** this design change does not alter personal keycard ownership, fixed spawn/reset rules, capture/drop recovery, safe-room state, either vent route, Crawler targeting, Photon ownership or Level 1 completion. ## September 12 Crawler visual-parent drift video follow-up

**Confirmed runtime failure:** Greg's `monsterOff.mp4` shows a different failure from the known rigid-body corner clipping. The selected Crawler gameplay/visual parent remains on the vent route while the Zombie skinned presentation moves far away from that parent and periodically snaps back near it. This makes the monster appear outside the vents even when the authoritative navigation root is still in the correct area.

**Source finding:** `CrawlerBodyPathFollower` had become a one-time rigid alignment utility after the failed torso-deformation experiments. It corrected the FBX/chest pivot and floor during `Configure()` but performed no continuous alignment afterward. The Zombie FBX imports as a Generic rig, while the separate `mixamo.com.anim` clip drives the Zombie Animator. `applyRootMotion=false` is insufficient as an ownership boundary when translation exists as Generic skeleton/bone curves: an animated `mixamorig:Hips` position can move the skinned hierarchy relative to `CrawlerVisualAnchor` even though the NavMesh root itself never left the vent. The periodic return seen in the video is consistent with the animated translation looping/resetting rather than with normal NavMesh movement alone.

**Implemented on `fix/runtime-keycard-crawler-loading`:** `CrawlerBodyPathFollower` runs at execution order 300, after whole-visual heading (250) and before hand contact IK (350). The active ownership rule is gameplay/NavMesh/Photon owns world travel while the crawl clip owns pose only.

**Confirmed source self-review finding before headset retest:** the first in-place pass translated `Zombie Crawl` directly even though that imported root can also be Animator-owned. It could still look correct in a simple frame, but it left two systems with positional ownership of the same transform and its warning observed residual correction rather than total clip drift. That implementation is superseded before runtime testing.

**Implemented hardening:** `CrawlerBodyPathFollower` now inserts `CrawlerMotionCompensation` between `CrawlerVisualAnchor` and `Zombie Crawl`. Pivot/floor alignment and in-place cancellation move only this non-animated wrapper. `Zombie Crawl` and its `mixamorig:*` skeleton are never repositioned by the compensation code. After calibration, Hips is measured in compensation-wrapper local space; each frame the wrapper receives an **absolute** local position of `calibrated position - total horizontal X/Z travel drift`, so no correction accumulates and an animation loop returning to zero horizontal drift also returns the wrapper exactly to its calibrated position. Greg's next screenshot/log pass confirmed horizontal compensation was active (1.22 m attempted horizontal travel) but the core body still rendered too low. Positive/upward Hips motion remains authored; only negative Y root drift is now cancelled at the calibrated floor pose. The warning converts total horizontal drift to world meters. `CrawlerVisualHeadingStabilizer` explicitly obtains the stable `CrawlerVisualAnchor` from the follower rather than using `VisualRoot.parent`, preventing the new translation wrapper from accidentally becoming the heading node. `Tools/validate_level1_contracts.py` and `Tools/validate_pr15_review_hardening.py` fail if direct `visualRoot` correction or inferred-parent heading is reintroduced.

**Second pre-test source-review findings and fixes:** the serialized Crawler gameplay root still carries old MiniGamesKid orientation (`modelForwardOffset` 180 degrees and a legacy root roll/tilt), while its NavMeshAgent `m_BaseOffset` is `0`. `CrawlerVisualAnchor.localRotation = identity` therefore did not guarantee an upright **world** frame during the one-time body/floor calibration; the heading stabilizer corrected world orientation only later in `LateUpdate`. PR #15 now zeroes the old model-forward offset before calibration and initializes the visual anchor from flattened gameplay forward plus world up before the Zombie pose/bounds/Hips reference are measured. This prevents the calibration itself from being performed in the legacy tilted frame.

Greg's Console capture also exposed a separate cleanup defect: Unity reported `Can't remove Animator because RigBuilder (Script) depends on it`. The marker-based cleaner had correctly identified the old visual rig but its runtime path then attempted to destroy the root Animator while `RigBuilder` was still alive. Runtime cleanup now disables marker-confirmed root-only `RigBuilder`/`BoneRenderer` support and the obsolete root Animator for that session; it does not attempt the invalid Animator destroy. The explicit Editor migration, where immediate dependency-ordered removal is safe, deletes the support components before deleting the old root Animator. Regression checks now protect both the world-upright pre-calibration setup and the dependency-safe cleanup order.

**Validation boundary:** this source correction is intentionally being reviewed before Greg spends another headset test on it, but it is still not runtime-proven. Test multiple full animation loops in a straight vent before judging turns, confirming the core body stays at/above the vent floor while upward crawl/bob remains visible. ## September 13 VentRoom blower material runtime correction

Source contracts protect the built-in render-pipeline setting, each Standard material, importer GUID mapping, and the absence of dynamic URP/material creation.
