# Reusable physical keycard system

Review date: 2026-09-15 UTC. Implementation branch: `feature/keycard-reader-light-feedback`, PR #23. Review baseline: `17a3253921334733581fae9b361e796ed861a36e`. Unity **2022.3.55f1**, Photon PUN, XR Interaction Toolkit **2.6.4** (both manifest and lock file). The previous 2.5.4 references were documentation errors, not an installed-version change.

## Supported contract

These are **visit-local, personal, single-use physical objective cards**. Each client owns its scene copy; there is no network card transfer or shared card inventory. A card that has been held by the local rig can be presented to a matching, explicitly bound reader. Successful acceptance commits the card as consumed before notifying progress listeners, increments exactly one lock, disables acquisition, and destroys the card. A rejected attempt remains retryable. Leaving and reloading a level creates fresh cards/progress through the existing scene lifecycle.

For Level 1, the two authored cards remain Amber Triangle, the two-card count and Level 2 travel guards remain unchanged, and the Crawler/capture/zone/networking systems are not rewritten. Reading a card changes the reader's immediate feedback; the separate panel owns persistent accepted progress. Prior 0/2 -> 1/2 runtime success is historical and narrow. The reported stuck hands/forcefield/repeated-pickup failures remain unclosed until retested on the reviewed code.

A lock can have multiple explicitly bound readers. It currently counts **accepted distinct physical cards**, not a per-credential checklist. Two Amber submissions do not mean one Amber plus one Cyan. Per-credential quotas, reusable/non-consumed passes, cross-level saved reward cards, object pooling of consumed cards, shared multiplayer cards, and network-authoritative inventory are **not implemented or approved by this review**. Do not repurpose these visit-local instances for those contracts without a separate design and lifecycle change.

## Author a card and reader in another level

### September 22 interaction correction

Greg's branch retest reports excessive attraction distance, failed repeat pickup, immovable loose cards and a grip-edge rendering defect. These remain open headset acceptance items. Bootstrap now configures both direct interactors with an **8 cm sphere**, **Improve Accuracy With Sphere Collider enabled**, Default-layer overlap queries and **Physics Trigger Interaction = Collide**. XRI 2.6.4 requires one SphereCollider and no Rigidbody on that same interactor GameObject to use this query path; copying only the enable flag onto a different hierarchy may fall back to trigger events. This explicit query can detect a stationary/sleeping acquisition trigger without waiting for a new trigger callback. The previous 60 cm spheres are superseded.

`KeyCard` also filters new selection/hover to a **local XRDirectInteractor within 10 cm of the solid card surface**, measured from its palm attach point. Oversized or swept volumes and ray interaction cannot acquire a distant card. Already-selected holders remain valid beyond that distance so physical wall resistance does not cause an unintended drop. These are initial tuning values requiring real hand/Quest validation. The smaller Bootstrap direct-hand volume also affects other directly grabbed props; retest those interaction points when changing the shared rig.

Gorilla locomotion excludes only eligible loose card solids from support queries, continues to find actual floor/wall geometry, and applies bounded hand impulses along the resolved virtual-hand movement. No collision layers or global trigger-query settings are changed. A card remains a solid Rigidbody prop; readers still require its root solid collider. The corrected Amber FBX removes overlapping shell/grip edge faces without changing its GUID, dimensions or color/symbol identity.

### Card and reader setup

Create a gameplay root with `KeyCard`, `BoxCollider`, `Rigidbody`, `XRGrabInteractable`, `HeldItemCollisionMode` and an appropriate `RespawnToOriginalSpawn` configuration. Put the badge mesh beneath that root. Set a supported explicit credential: Amber Triangle, Cyan Three Bars, Red Circle or Violet Diamond. Do not combine the physical `KeyCard` with legacy `VRKeyCard`, which uses a collect-and-destroy inventory path. Do not place it under a PhotonView or a second card's Rigidbody.

Startup fits the solid collider from renderer-local mesh bounds and normalizes the lightweight body plus **VelocityTracking** grab movement. Trails/particles and nested other cards are excluded from the fit. This supersedes the imported Instantaneous movement setting, which did not honor the intended physics-driven held prop. The acquisition collider is a separate child trigger, `Keycard_GrabAffordance`; it must not share a GameObject/layer-changing solid collider. The root solid collider alone is accepted for scanner geometry. Initial scale should be positive and nonzero; avoid sheared/nonuniformly scaled ancestor hierarchies. Run the runtime scale/rotation tests before using a new physical shape. A future interactor movement override must not silently switch these cards back to Instantaneous.

Create the intended `KeyBox`, set `keysNeeded >= 1`, and enable **Require Matching Reader**. New and migrated locks, including runtime-created ones, default to that setting even before readers initialize. An intentional legacy opt-out must be explicit; existing serialized opt-outs are preserved. Assign the reader's `keyBox`, or deliberately nest exactly one box under its `readerRoot`. Give the reader one enabled trigger BoxCollider on its controller object, an explicit credential and valid status renderer/materials. A gameplay reader binding also latches its box into reader-only mode for that visit, so disabling or unbinding the reader cannot reopen direct insertion. Keep the explicit flag enabled for objectives whose readers start inactive. Unbound legacy boxes may intentionally retain direct insertion; their public `TryAddKey` now also consumes on success rather than providing a second count-only entry point.

Place the separate progress panel, explicitly bind its box, and author one unique lamp renderer for each required card. The current reusable prefab contains **four slots**, previews two, and needs expansion for larger locks. Inadequate capacity or missing/duplicate/root/external lamp references log a warning and keep safely authored lamps amber rather than showing false completion. Invalid references are never used to toggle the panel root or unrelated objects. Lamp renderers must be children of the panel, not its root/ancestor or an unrelated object. Different scenes cannot share a live objective binding.

Use `reader.BindObjective(source)` and `panel.Bind(source)` for dynamic setup. `Bind(null)` is an explicit unbind and will not silently rediscover an old nested/parent source. A reader attempts authored discovery once; late-created objectives must bind explicitly. Rebinding clears overlap/presence state and prevents an old acceptance callback from flashing the new binding. Re-enable/rebind performs a bounded-frequency nearby collider rescan after physics updates, including sleeping cards that may not produce a fresh trigger entry.

For multi-storey maps, configure fall recovery **below the lowest playable route**, not merely three metres below a high pickup shelf. The existing spawn-relative threshold is suitable only where that vertical difference is out of bounds. Recovery now survives temporary object deactivation, wakes a loose body to settle under gravity, and never re-enables a consumed card. Disabling only the held-collision safety behaviour keeps existing protection while the prop remains active; re-enabling resumes separation cleanup. Whole-object deactivation/destruction restores the owned state, and reactivation retains separation protection. Independently nested grabbables are not part of the prop/player collider set.

## Read-only authoring checks

Stop Play Mode, then run:

- **Tools > Runaway Chimps > Cards > Validate Loaded Scenes**: checks active objects in loaded scenes; inactive historical experiments are deliberately excluded.
- **Tools > Runaway Chimps > Cards > Validate Selected Prefab or Hierarchy**: checks the selected hierarchy, including inactive children, before reusing it elsewhere.

The validator checks component/credential setup, legacy inventory conflicts, personal-card Photon ownership mistakes, nested/extra collider bodies, positive scale, authored binding, reader triggers/materials, panel capacity and lamp wiring. It never saves a scene, changes a prefab, or applies SerializedObject changes. Template/unbound assets can intentionally report warnings/errors until authored for gameplay. Dynamic bindings must be independently verified in Play Mode. A successful authoring report is not a physics or multiplayer test.

Eight existing intentionally broken source fixtures and fourteen geometry-math fixtures remain. These cannot establish Unity compilation or PhysX behavior.

**Managed production-state tests:** `dotnet run --project Tools/CardSystemHarness/CardSystemHarness.csproj --configuration Release` compiles the **actual** engine-independent production `CardConsumptionState.cs`. It exercises reference-identity locks, rejection/retry, reservation ownership, consumption-before-observer visibility, reentrancy and duplicate-credit rejection across 1,000 repeated sequences. It does not replace the engine: no XRI, Rigidbody, trigger, travel or Photon execution is claimed.

**Unity Play Mode fixtures (implemented, pending execution):** open **Window > General > Test Runner > PlayMode**, filter `RunawayChimps.Tests.CardSystemPlayModeTests`, and run the fixture in an empty test context with the project packages installed. The test assembly uses TestAssemblies/UNITY_INCLUDE_TESTS and does not create a second runtime game rig. Because production remains in Assembly-CSharp, only the test's boundary uses reflection; no application assembly reorganization is required.

The cases cover all 16 reader/card credential pairings, reader-required non-Level-1 locks, public direct-call rejection, unheld then eligible retry, cross-lock/cross-reader duplicate attempts, in-progress observer exceptions, explicit unbinding, stale and accessory overlap, disabled components/body collision, panel rebind and insufficient capacity, six 1x/2x rotation cases, actual programmatic XRI selection, live collider-map registration, recovery across deactivation, sleeping-card rediscovery, gravity settling and wake-after-recovery. Then complete repeated real-controller pickup/drop/immediate-re-grab, hand changes, flat/rotated/floor/wall cases, body/head proximity and held-card wall contact.
